# 개인 할 일 관리 서비스 — 설계

작성일: 2026-07-31

## 1. 배경과 목표

기존 일정관리 도구(구글 캘린더, 노션)는 두 가지 이유로 정착하지 못했다.

1. 기능이 많아 입력 자체가 부담스럽다
2. 내가 일을 떠올리는 방식(시간표가 아니라 순서가 매겨진 목록)과 구조가 맞지 않는다

따라서 이 서비스의 성공 기준은 기능의 개수가 아니라 **계속 쓰게 되는가**이다. 설계상의 모든 선택은 입력 마찰을 낮추고 화면을 단순하게 유지하는 쪽으로 판단한다.

목표를 한 문장으로: **한 줄로 던져 넣고, 중요도 3단계로 나뉜 전체 목록을 한 화면에서 보는 개인용 할 일 관리 웹앱.**

### 범위 밖 (명시적으로 만들지 않는 것)

- 다른 사용자와의 공유, 협업, 권한 관리
- 시간 단위 캘린더 격자, 시간 블록 배치
- 예약·진료 관리 기능
- 반복 일정 자동 생성
- 알림·푸시
- 오프라인 동작

## 2. 도메인 모델

할 일(task) 하나가 전부이며, 테이블도 하나다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → auth.users | RLS 기준 |
| `title` | text, not null | 한 줄 제목 |
| `bucket` | enum: `today` \| `week` \| `someday` | 중요도 그룹 |
| `position` | numeric | 그룹 내 정렬값 (분수 순위) |
| `bucketed_at` | timestamptz, not null | 현재 bucket으로 들어온 시각 |
| `done_at` | timestamptz, null 허용 | null이면 미완료 |
| `created_at` | timestamptz, not null | |

태그, 마감일, 하위 항목, 메모, 첨부는 **없다.** "한 줄 던지기"라는 입력 방식과 맞지 않고, 실제로 아쉬워졌을 때 추가해도 늦지 않다.

### 정렬: 분수 순위 (fractional index)

`position`은 정수 인덱스가 아니라 실수다. A(1.0)와 B(2.0) 사이에 끼워 넣을 때 1.5를 주면 끝나므로, 드래그 한 번에 목록 전체를 다시 번호 매기는 쓰기 폭발이 없다.

- 목록 맨 위로: 현재 최솟값 − 1
- 맨 아래로: 현재 최댓값 + 1
- 사이: 위아래 값의 평균

부동소수점 정밀도가 고갈되는 경우(같은 두 항목 사이에 50회 이상 반복 삽입)는 해당 그룹만 1.0 간격으로 재배열한다. 이 재배열 조건과 순위 계산은 순수 함수로 분리해 단위 테스트한다.

### 오래된 항목 표시

`today`에 들어온 지 **3일**이 지났는데 아직 `done_at`이 null이면 제목 옆에 흐린 점(`·`)을 표시한다. 위치는 바꾸지 않고, 자동으로 다른 그룹으로 옮기지도 않는다. 묻혀가는 항목을 보이게 하되, 내가 정한 순서를 시스템이 흔들지 않는다는 원칙이다.

기준 3일은 `bucketed_at`으로 계산하며, 상수 하나로 분리해 나중에 조정할 수 있게 둔다.

### 완료 처리

체크하면 `done_at`이 채워지고 목록 하단의 접힌 "완료" 영역으로 이동한다. 이 영역은 기본으로 접혀 있고, 오늘 완료한 항목의 개수만 보인다. 완료 항목은 삭제하지 않고 보관한다 — 통계와 되돌리기의 근거가 된다.

완료 영역에서 체크를 해제하면 `done_at`이 다시 null이 되고 원래 그룹의 원래 자리로 돌아간다. `bucket`과 `position`은 완료 시점에 바뀌지 않으므로 별도 기록 없이 복귀할 수 있다.

## 3. 화면

라우트는 하나(`/`)다. 설정 페이지도, 상세 페이지도 없다.

### 본문 (모든 화면 크기 공통)

```
┌────────────────────────────────┐
│  + 할 일 입력...               │
├────────────────────────────────┤
│  오늘                        3 │
│   ⠿ 진료기록 정리              │
│   ⠿ 세금계산서 발행         ·  │
│   ⠿ 은행 다녀오기              │
│                                │
│  이번주                      2 │
│   ⠿ 논문 초록 마무리           │
│   ⠿ 노트북 백업                │
│                                │
│  언젠가                      4 │
│   ⠿ 스터디 자료 정리           │
│                                │
│  ▸ 완료 (오늘 2개)             │
└────────────────────────────────┘
```

- 입력창은 화면 상단에 고정되고, 페이지 진입 시 자동으로 포커스를 받는다. 타이핑 → 엔터 → 계속 타이핑이 끊기지 않아야 한다.
- 새 항목은 `today` 그룹의 맨 아래로 들어간다.
- 세 그룹은 세로로 이어진다. 스크롤은 한 줄기이며, PC와 모바일이 같은 구조다.
- 항목은 그룹 안에서도, 그룹을 넘어서도 드래그로 옮길 수 있다. 그룹 경계를 넘으면 `bucket`과 `bucketed_at`이 함께 갱신된다.
- 제목을 클릭하면 그 자리에서 편집된다. 엔터 또는 포커스 이탈로 저장, Esc로 취소.
- 삭제는 항목에 마우스를 올렸을 때(모바일에서는 왼쪽으로 밀었을 때) 나타나는 × 버튼으로 한다. 확인 창은 띄우지 않고, 대신 토스트에 "실행 취소" 버튼을 5초간 띄운다. 확인 창은 마찰이고, 되돌리기는 마찰이 아니다.

### 사이드바 (가로 1024px 이상에서만)

왼쪽 고정 폭 220px. 두 가지만 담는다.

1. **상태 요약** — 오늘/이번주/언젠가의 미완료 개수, 오늘 완료한 개수
2. **검색** — 입력하면 본문 목록이 검색 결과 목록으로 바뀐다. 완료 항목 포함 여부 토글 하나. 입력을 비우거나 Esc를 누르면 원래 목록으로 돌아온다. 검색 결과에서는 드래그가 비활성화된다 — 순서가 그룹 기준이 아니므로 끌어다 놓을 자리가 정의되지 않는다.

1024px 미만에서는 사이드바가 사라진다. 요약은 헤더의 한 줄(`오늘 3 · 이번주 2 · 언젠가 4`)로 축약되고, 검색은 헤더의 아이콘을 눌러 여는 오버레이가 된다.

사이드바에 그룹 네비게이션은 넣지 않는다. 세 그룹이 이미 한 화면에 다 보이므로 이동할 곳이 없다.

## 4. 아키텍처

| 층 | 선택 |
|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript |
| 배포 | Vercel |
| 데이터 | Supabase Postgres |
| 인증 | Supabase Auth — 이메일 + 비밀번호 |
| 접근 제어 | RLS: 모든 작업에 `user_id = auth.uid()` |
| 쓰기 경로 | Server Actions |
| 드래그 | dnd-kit |
| 모바일 | 반응형 + PWA (홈 화면 추가용) |

인증은 매직 링크가 아니라 이메일과 비밀번호를 쓴다. 매직 링크는 휴대폰에서 기본 브라우저로 열리는 탓에 홈 화면에 추가한 PWA와 세션이 어긋나기 쉽고, 자동화된 E2E 테스트로 로그인 흐름을 검증할 수 없다. 혼자 쓰는 앱이라 가입 경험을 다듬을 이유도 없으므로, 계정은 Supabase 대시보드에서 하나만 미리 만들고 앱에는 로그인 폼만 둔다. 가입 폼을 아예 두지 않는 것이 남이 계정을 만들지 못하게 막는 가장 확실한 방법이다.

PWA는 홈 화면 아이콘으로 앱처럼 열기 위한 것이지 오프라인 동작을 위한 것이 아니다. manifest와 아이콘에 더해 fetch 핸들러를 가진 최소 서비스 워커를 하나 둔다 — Android Chrome이 설치를 허용하려면 필요하기 때문이며, 캐싱 전략은 넣지 않고 요청을 그대로 통과시킨다.

### 데이터 흐름

초기 목록은 서버 컴포넌트에서 읽어 렌더한다. 이후의 모든 변경(추가, 완료, 순서 변경, 그룹 이동, 삭제)은 **낙관적 업데이트**로 처리한다. 화면은 즉시 바뀌고 Server Action이 뒤에서 저장한다. 실패하면 이전 상태로 되돌린다.

이것이 local-first 대신 선택한 절충이다. 체감 즉시성은 대부분 얻으면서, 기기 간 충돌 해소라는 어려운 문제는 떠안지 않는다. 혼자 쓰는 앱이므로 두 기기에서 같은 항목을 동시에 고칠 일이 사실상 없다.

### 모듈 경계

각 단위는 하나의 목적을 갖고 독립적으로 테스트 가능해야 한다.

- `lib/ranking.ts` — 분수 순위 계산. 순수 함수. DB도 React도 모른다.
- `lib/tasks/queries.ts` — 읽기. Supabase 클라이언트를 받아 task 배열을 돌려준다.
- `lib/tasks/actions.ts` — 쓰기 Server Actions. 입력 검증 후 queries 계층 호출.
- `components/TaskList` — 그룹 렌더와 드래그. 순위 계산은 `lib/ranking`에 위임한다.
- `components/QuickAdd` — 입력창. 제출 콜백만 받는다.
- `components/Sidebar` — 요약과 검색. 집계값을 props로 받고 스스로 조회하지 않는다.

컴포넌트가 Supabase를 직접 부르지 않는 것이 핵심 규칙이다. 그래야 UI를 데이터 없이 테스트할 수 있다.

## 5. 오류 처리

| 상황 | 동작 |
|---|---|
| 저장 실패 (네트워크·서버) | 낙관적 변경을 롤백하고 하단에 토스트: "저장하지 못했습니다" + 다시 시도 버튼 |
| 연속 실패 | 토스트를 쌓지 않고 하나로 유지하며 개수만 갱신 |
| 세션 만료 | 로그인 화면으로 보내되, 입력 중이던 텍스트는 localStorage에 임시 보관해 복귀 후 되살린다 |
| 빈 제목 제출 | 아무 일도 하지 않는다. 오류 메시지 없음 |
| 초기 로드 실패 | 목록 자리에 오류 메시지와 새로고침 버튼 |

오프라인 큐는 만들지 않는다. 실패는 롤백과 재시도 버튼으로만 다룬다.

## 6. 테스트

버그가 날 가능성과 테스트 비용을 함께 보고 세 층으로 나눈다.

1. **단위 — `lib/ranking.ts`**: 맨 위/맨 아래/사이 삽입, 빈 목록, 단일 항목, 정밀도 고갈 시 재배열. 이 프로젝트에서 가장 미묘한 로직이므로 여기에 테스트를 집중한다.
2. **통합 — Server Actions**: 로컬 Supabase 인스턴스를 띄우고 추가·완료·그룹 이동·삭제를 검증한다. RLS가 남의 행을 실제로 막는지도 여기서 확인한다.
3. **E2E — Playwright 한 흐름**: 로그인 → 한 줄 입력 → 목록에 등장 → 체크 → 완료 영역으로 이동. 회귀를 잡는 최소한의 그물.

컴포넌트 스냅샷 테스트는 만들지 않는다. 유지 비용에 비해 잡아내는 것이 적다.

## 7. 열린 항목

- 프로젝트 폴더 이름은 `sunseo`로 잡았다(순서축이 핵심이라는 뜻). 바꾸고 싶으면 구현 시작 전에 정한다.
- "오래됨" 기준 3일은 상수로 두고, 실제로 써보며 조정한다.
